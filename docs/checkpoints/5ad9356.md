# Checkpoint — `5ad9356` multi-material GLB primitive validation

Implementation revision: `5ad9356a0938178d19b933c4ba363f58cd233a61`.
Base revision: `4777075e046b690498bd689fa3a77aeb13ff7559`.
Reusable capability: distinguish authored Three.js mesh ownership from glTF render primitives so semantic multi-material surfaces survive the local/gallery export loop without false round-trip failures, while malformed material-group ownership fails before export.

## Authoring change

The preceding semantic material-region workflow exposed a real export-loop assumption: one authored Three.js `Mesh` with many material groups exports as several glTF primitives, and locked Three.js r186 reloads those primitives as several `Mesh` objects. The prior bake compared raw `Mesh` counts, so `material-regions-study` failed with `29 !== 4` even though triangles, bounds and material partitions were intact.

`inspect()` now reports `primitives` separately from logical `meshes`. Single-material meshes contribute one primitive; multi-material meshes contribute their geometry-group count and are preflighted for non-empty groups, valid material indices, and valid triangle-aligned group ranges. `scripts/bake.mjs` now treats render-primitives, triangle count and bounds as the GLB round-trip invariants while retaining logical mesh count as a useful authoring statistic.

## Research influence

- Khronos **glTF 2.0 Specification — Meshes** defines a mesh as an array of primitives and notes that splitting a mesh into primitives is useful for assigning different materials to different parts. Adaptation: use primitive count, not application object count, as the portable material-partition invariant.
- Three.js r186 **GLTFExporter** iterates `BufferGeometry.groups` for multi-material meshes and emits a primitive for every group; a multi-material mesh without groups is not exportable. Adaptation: mirror that ownership contract in `inspect()` before browser/export work starts.
- Three.js GLTFLoader issue #30090 documents that a glTF mesh with multiple primitives is represented as a `THREE.Group` with one `THREE.Mesh` per primitive. Adaptation: explicitly regression-test object-count expansion rather than accidentally treating it as corruption.

Detailed observations, tests and limitations are in `docs/research/gltf-render-primitives.md`.

## Rejected approaches

- Do not merge or split authored components merely to force Three.js object counts to match after GLB reload; that would damage useful construction ownership to satisfy a loader hierarchy detail.
- Do not weaken triangle or bounds validation; those remain required round-trip invariants.
- Do not treat raw `Mesh` count as a cross-format invariant when a logical mesh legitimately contains multiple material primitives.

## Remaining limitations / next priority

Primitive-count equivalence verifies render partition ownership, not semantic node naming, numerical material equality, skin/animation correctness, or arbitrary loader hierarchy stability; those remain independent checks. Group preflight intentionally covers the exporter-visible ownership contract rather than becoming a general scene validator.

With semantic multi-material assets now represented correctly in the export loop, the next general workflow priority returns to **UV chart inspection and deterministic atlas packing for already-authored charts**: overlap/bounds/stretch diagnostics plus reusable placement of multiple semantic charts before considering a more complex unwrap solver.
