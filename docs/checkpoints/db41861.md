# Workflow checkpoint — curve-guided broad deformation

Capability: reroute existing indexed `BufferGeometry` along short authored 3D centerlines while retaining topology, UVs, ordinary custom attributes, semantic face regions and the existing pre-rig ownership contract.

## Accepted change

`src/lib/geometry-deform.js` adds `deformationCurve()` and `curveVertices()` on top of the existing local deformation-handle API. A guide stores JSON-safe handle-local control points, one initial up vector, Catmull-Rom interpolation settings and bounded frame resolution. Evaluation maps the handle-local +Y range to equal-distance positions along the guide and reuses `src/lib/curve-frame.js` transported frames to carry the source X/Z cross-section. Two-point guides use `LineCurve3`; longer guides use locked Three.js r186 `CatmullRomCurve3`.

Points beyond the bounded handle range continue along endpoint tangents. A straight +Y guide is tested as an identity mapping. Existing bend/twist/taper behavior and defaults remain unchanged; curve deformation is opt-in and composes sequentially with those operations and ordinary point-domain selections.

This is deformation of existing geometry, not a sweep constructor. Use `profile-sweep.js` when new topology should be generated from a profile and centerline.

## Research used

See `docs/research/curve-guided-deformation.md`.

- Blender 4.5 Curve Modifier: dominant-axis deformation, perpendicular offset and endpoint-direction continuation informed the bounded +Y mapping and tangent continuation. The repository does not reproduce Blender object dependencies, axis switches, radius/tilt controls or global placement semantics.
- Hanson & Ma, *Parallel Transport Approach to Curve Framing* (1995): parallel-transport frames avoid the curvature-normal dependency of Frenet frames near low curvature/inflection. Adaptation: reuse the repository's already-tested finite `transportedFrames()` implementation rather than adding another framing algorithm.
- Three.js r186 Curve/CatmullRomCurve3: arc-length-aware `getPointAt()`/`getTangentAt()` and spline configuration provide the locked runtime interpolation primitives; authored guide data remains plain JSON.

## Rejected approaches

- Did not stack several manually positioned circular bend handles; that preserves the repeated authoring pain the guide is meant to remove.
- Did not replace the source mesh with a profile sweep; the acceptance target is topology-preserving rerouting of existing UV/attribute/region ownership.
- Did not adopt a renderer-only curve-flow modifier or new dependency; deformation stays CPU-side in the existing local authoring/export loop.

## Remaining limitations / next workflow priority

The guide is a finite sampled deformation, not a collision solver or length-preserving material model. Guide length can stretch/compress axial spacing; control points do not yet own radius/tilt channels; strong paths can self-intersect; frame interpolation remains resolution-dependent; rig/morph refit is still rejected. The next general workflow priority is a compact **lattice/box free-form deformation** for broad asymmetric volume edits where one centerline is insufficient, exercised on an organic volume and an unrelated hard-surface prop without remeshing or rig ownership. No cyber-android likeness change is claimed in this pass.
