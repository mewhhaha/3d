# Workflow checkpoint — exact persistent-anchor remap through solidify

Base remote revision: `0114428b999ba68056800d4279135fdc0c33e9d6`.
Implementation revision: `d309b6c3d20f8ba985ffd8b2ef6adf333e2f0682`.
Capability: keep one authored barycentric attachment spot exact when a known topology constructor changes the mesh, starting with the outer/inner face copies created by `solidifyGeometry()`.

## Accepted change

`surfaceTopologySignature()` now fingerprints indexed topology without including vertex positions, so anchors created by `bindSurfaceAnchor()` remain valid through same-topology form edits but fail explicitly when index topology changes. `remapSurfaceAnchor()` is the generic constructor-owned remap primitive: callers provide the exact target triangle and a target-corner → source-corner permutation, and the helper remaps barycentric coordinates plus affine tangent weights together.

`solidifyGeometry()` records source triangle count and source topology signature. `remapSolidifyAnchor()` consumes that provenance to map a source anchor to the exact outer or inner face copy. Outer faces preserve corner order. Inner faces reverse winding, so the remap uses `[0, 2, 1]`. Rim remap is deliberately unsupported because one source face may contribute zero or multiple boundary edges; a face-only source anchor does not identify one exact rim face.

Legacy serialized anchors without a topology signature retain the older face/corner checks for compatibility, but anchors newly produced by `bindSurfaceAnchor()` are strict.

## Research used

See `docs/research/surface-anchor-remap.md`.

- Blender 4.5 LTS **Extrude Mesh** documents generated Top/Side geometry and explicit face/corner attribute propagation. Adaptation: consume exact constructor-owned face/corner provenance instead of recovering attachment intent with nearest-surface search after topology changes.
- Blender 4.5 LTS **Solidify** distinguishes shell and rim geometry and describes the simple method as extrusion-like. Adaptation: expose only the outer/inner one-to-one face copies in v1; reject ambiguous rim remap.
- Three.js r186 **Triangle** and **BufferGeometry** define barycentric coordinates over ordered triangle corners and indexed faces through ordered vertex indices. Adaptation: permute barycentric and tangent weights whenever target winding changes.

## Ownership and limitations

This is exact construction provenance, not general remeshing correspondence. V1 supports only known one-to-one face copies whose target corner order is supplied explicitly. It does not remap to solidify rims, booleans, subdivision, decimation, arbitrary remeshes or unrelated reconstructions. The topology signature is a deterministic practical guard, not a cryptographic asset identity. Persistent anchors remain authoring metadata and are not exported as glTF semantics; the helper still binds a rigid component frame rather than deforming an attached mesh or solving collision.

## Rejected approach

Do not let a bind-created anchor resolve directly on topology-changed output just because its original face index and corner numbers happen to remain in range; the full indexed-topology signature now blocks that accidental success. Do not nearest-project an exact anchor onto a shell when the constructor already knows the source face/corner relationship. Do not guess a rim face from only a source face-level anchor.

## Next workflow priority

Extend the same exact remap contract through **owned geometry composition**. `composeGeometries()` already knows each part's face/vertex offsets; remapping a component-local persistent anchor through composition would let later assembly, attachment and query stages operate on one combined topology without rebinding or dropping semantic part ownership.
