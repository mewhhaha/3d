Validated implementation revision: `e4c5b590e6d2662a024387de5074d73544c6ec9c` (API introduced by `438b646d12deca714b55a197cbd7373b4151aeaa`; focused render workflow added by `793627629614d4754bd9ebddbf341d0aed3188a7`).

## Reusable capability

This checkpoint adds a general authored-shot layer rather than another reference-specific camera/light table:

- `framedPerspectiveCamera(subject, spec)` solves a perspective-camera distance from the subject's actual bounds plus explicit direction/FOV/aspect/occupancy intent. Target remains separately editable and defaults to the bounds center.
- `inspectShotFraming(camera, subject)` reports projected NDC bounds, occupancy and clipping for mechanical review.
- `punctualLight(spec)` builds only portable directional/point/spot lights. Aimed lights align local `-Z` with the Three.js runtime target and preserve the tagged target-child contract already used by scene hydration.
- `punctualLightRig(subject, spec)` turns authored relative offsets into subject-scale-aware placements instead of repeated absolute world coordinates.
- `authoredShot({...})` assembles separately owned subject/environment/light/camera objects and writes the existing `sceneRecipe` metadata consumed by hero rendering.

Before this capability, reusable preview lighting existed but authored scenes still needed recipe-specific camera distance, target, and light coordinates (the older cyber stage is one example). New subjects can now change size while retaining the same framing/rig construction intent, or use entirely different camera/light designs through the same API.

## Research → implementation

Accessed 2026-09-17; full notes are in `docs/research/authored-shot-lighting.md`.

- Three.js PerspectiveCamera documentation: https://threejs.org/docs/pages/PerspectiveCamera.html — FOV/aspect/near/far are explicit camera properties. Adaptation: solve only the distance needed to fit actual authored bounds; do not infer artistic composition.
- Three.js DirectionalLight / PointLight / SpotLight documentation: https://threejs.org/docs/pages/DirectionalLight.html , https://threejs.org/docs/pages/PointLight.html , https://threejs.org/docs/pages/SpotLight.html — directional/spot runtime direction depends on targets, while point lights are omnidirectional and inverse-square decay is the physically correct point/spot setting. Adaptation: preserve explicit target data while keeping color/intensity placement independent.
- Khronos `KHR_lights_punctual`: https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_lights_punctual/README.md — portable glTF lighting is directional/point/spot and directional/spot emit along node-local `-Z`. Adaptation: restrict the exportable helper to those three types and align local `-Z` with Three's runtime target instead of inventing an area-light approximation.
- Blender Light Objects: https://docs.blender.org/manual/en/dev/render/lights/light_object.html — point/spot/sun/area lights have distinct artistic/physical roles. Adaptation: keep punctual rigs deliberately separate from future area/environment lighting and from preview-only studio presets.

## Ownership and portability guarantees exercised

The helpers return ordinary Three.js cameras/lights/groups and do not introduce a proprietary renderer object. Subject meshes, environment objects, camera, and lighting remain separately named children. Preview `studio-lighting.js` remains separate. Hero rendering resolves the named authored subject/camera through existing metadata; neutral inspection passes hide the canonical `AuthoredSceneLights` group rather than mutating exported materials or geometry. Tests serialize/parse an authored shot and explicitly rehydrate aimed-light targets.

## Rejected approaches

- Hard-code another camera distance/light coordinate set in each model: fast for one fixture, but repeats the current pain and scales poorly when subject dimensions change.
- Automatically infer an attractive composition from bounds: bounds do not encode focal hierarchy, horizon, face orientation or reference intent, so the helper only solves the mechanical fit problem.
- Convert all lighting into one universal style preset: this would erase useful artistic differences; the two fixtures intentionally use different types/colors/angles through the same mechanics.
- Approximate area/environment lights as punctual emitters merely to preserve glTF export: rejected because it changes the intended lighting model. Portable punctual ownership and renderer-specific/environment lighting remain separate.
- Auto-rescale point/spot intensity when a subject grows: rejected for v1 because intensity units and artistic exposure intent are separate from placement scale.

## Limitations

Bounds fitting can leave extra negative space because an axis-aligned world box is intentionally conservative; explicit target choice still matters. There are no rule-of-thirds/face/horizon semantics, autofocus, collision-aware light placement, light linking, IES profiles, area/environment emitters, physical exposure calibration, automatic shadows, camera animation or cross-engine appearance guarantee. Point/spot intensity is not normalized when the rig scale changes. glTF portability of punctual types/camera data does not guarantee identical renderer tone mapping or shadow appearance. The API assumes one named authored subject and camera per shot rather than solving arbitrary nested scene dependencies.
